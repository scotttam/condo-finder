How Condo Finder works

One Django process on the Mac mini at home does everything. A scheduler inside it scrapes twelve listing sites five times a day into SQLite, and the same process serves the pages you two browse over Tailscale.

One scrape run, source by source

The runner works through the sources one at a time. A broken source records its error on the Sources page and the run moves on to the next one.

What's stored

A Listing is the apartment. A SourceListing is one site's ad for it. The same unit on Zillow, Redfin and Craigslist is one Listing with three SourceListings.

The Trends page adds two standalone tables. TrendReport keeps each analysis: the ranked picks (with a snapshot of address, photo and price when picked), Claude's market read, the statistics it was given, token usage and cost, and what changed since the previous report. SearchPriorities is one shared row holding "What we're looking for".

Rules the design depends on

  • One worker, one schedulerGunicorn must stay at workers = 1. More workers would each start a scheduler.
  • Units never cross-mergeTwo units at one address from the same site stay separate. Hidden addresses never merge.
  • Gone takes proofA listing needs three missed runs, or a direct page check, before it's marked gone.
  • Rents stay plausibleAnything over $25,000 is treated as a sale price or home value and ignored.
  • Polite by defaultEvery source has a delay and a detail-page budget. Redfin stops at the first bot challenge.
  • Claude sees a digest, not the databasePass 1 gets compact facts for about 600 candidates; only its 25-listing shortlist gets full descriptions in pass 2. That keeps a run near $0.50.
  • Deploy is one scriptgit pull && ./deploy/install.sh syncs, migrates, collects static files and restarts through launchd.
